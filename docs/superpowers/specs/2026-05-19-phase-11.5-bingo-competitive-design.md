# Phase 11.5 — Competitive Bingo + American Variant Design

**Author:** brainstormed 2026-05-19 with user
**Status:** Spec — pending implementation plan
**Phase:** 11.5 (post-Phase-11 expansion; replaces shipped solo bingo)
**Goal:** Replace shipped solo bingo with a competitive mode against AI opponents, and add an American 75-ball 5×5 variant alongside the existing British 90-ball 3×9 game.

---

## 1. Context

Phase 11 (shipped 2026-05-19, tag `v0.11-bingo`) gave us solo British 90-ball bingo: 1–4 cards, fixed-tier payouts per card (line 25, two-line 75, full house 250, fast-FH bonus 500). The user has decided that model isn't what they want.

The replacement:

- A **competitive** model where the player races a configurable number of AI opponents to call BINGO first.
- A **second variant** — American 5×5 with free centre square — picked at lobby time.
- A **difficulty system** (Easy / Medium / Hard) that controls opponent count, pot size, opponent reaction speed, and whether daubing is auto or manual.

The architecture remains games-sandbox-compliant (no `@/db/*` or `@/store/*` imports from `src/games/**`). Settle still writes one `rounds` row per game via `wallet.settleRound`. The existing `Round.game = 'bingo'` enum value is reused — `details` shape changes but the enum stays.

Clicking the **Bingo** cabinet on the lobby page opens a modal — it does NOT navigate directly.

The sidebar entry `🎯 Bingo` continues to point at `/play/bingo` for muscle-memory continuity; that lands at the redirect which sends the user back to the lobby and (in a future polish iteration) could trigger the modal automatically. For Phase 11.5 the redirect is enough.

## 3. Variants

Both variants share a single `BingoCard.tsx` component and a single `logic.ts` module driven by a `VARIANTS` config object.

```typescript

  rows: number; // 3 | 5
  cellsPerCard: number; // 15 (filled) | 24 (filled, excluding free centre)
  ballCount: number; // 90 | 75
  columnRanges: [number, number][];
  hasFreeCenter: boolean;
  tier1Label: string; // 'LINE!'
  tier2Label: string; // 'DOUBLE LINE!' | 'FOUR CORNERS!'
  tier3Label: string; // 'BINGO!' | 'BLACKOUT!'
};

const VARIANTS: Record<Variant, VariantConfig> = {
  british: {
    cols: 9,
    rows: 3,
    cellsPerCard: 15,
    ballCount: 90,
    columnRanges: [
      [1, 9],
      [10, 19],
      [20, 29],
      [30, 39],
      [40, 49],
      [50, 59],
      [60, 69],
      [70, 79],
      [80, 90],
    ],
    hasFreeCenter: false,
    tier1Label: 'LINE!',
    tier2Label: 'DOUBLE LINE!',
    tier3Label: 'BINGO!',
  },
  american: {
    cols: 5,
    rows: 5,
    cellsPerCard: 24,
    ballCount: 75,
    columnRanges: [
      [1, 15],
      [16, 30],
      [31, 45],
      [46, 60],
      [61, 75],

    tier1Label: 'LINE!',

  },

```

### Card generation

- **British (existing rules):** 15 cells distributed over a 3×9 grid; each row has exactly 5 filled cells; each column has 1–3 filled cells with values sorted ascending; column values drawn from the column's range with within-column uniqueness.
- **American (new):** 5×5 grid; the centre cell (row 2, col 2, zero-indexed) is marked `{ value: 0, free: true }` and counts as auto-daubed from the start; the other 24 cells take values from their column's range (B 1–15, I 16–30, N 31–45, G 46–60, O 61–75) with within-column uniqueness.

### Win tiers (per card)

- **Tier 1 — Line:** British = any row complete (5 filled cells of that row all daubed). American = any 5-in-a-row across any row, column, or diagonal (free centre counts as daubed).
- **Tier 2 — Two-Line (British) or Four-Corners (American):** British = any two complete rows. American = all four corners daubed (free centre is irrelevant to this pattern).
- **Tier 3 — Full House (British) or Blackout (American):** all 15 (British) / all 24 non-free (American) cells daubed. Free centre always counts as daubed for blackout.

Internal API uses generic `tier1 / tier2 / tier3` so machine code is variant-agnostic; variant config supplies user-facing labels.

## 4. Game economy

### Constants

```typescript
const BUY_IN = 50;

const DIFFICULTY = {
  easy: { cpuCount: 2, potMultiplier: 2, cpuLatencyMs: [200, 500] as const, forceManual: false },
  medium: { cpuCount: 5, potMultiplier: 4, cpuLatencyMs: [100, 250] as const, forceManual: false },
  hard: { cpuCount: 9, potMultiplier: 8, cpuLatencyMs: [0, 0] as const, forceManual: true },
} as const;

const LINE_BONUS = 10; // tier 1
const TWO_LINE_OR_4CORNERS_BONUS = 20; // tier 2
// tier 3 winner takes pot

// Pot = BUY_IN * potMultiplier
//   Easy   = 100
//   Medium = 200
//   Hard   = 400
```

### Card count

The user always has **exactly 1 card** in competitive mode. There is no card-count picker. Each CPU also has exactly 1 card. Total cards on the table = `1 + cpuCount`.

This is a hard simplification from solo bingo's 1–4 cards. It avoids the positive-EV exploit where buying 4 cards on Easy made bingo a guaranteed chip printer.

### Stake and pot

- User pays `BUY_IN` (50 chips) once per game, via `wallet.placeBet` at `BUY & PLAY`.
- Pot is `BUY_IN * potMultiplier`, funded conceptually by the house — no chip movement happens for the pot until settle.
- On user win (tier3 by user): user receives `pot` chips via `wallet.settleRound({ won: true, payout: pot + bonusesEarned })`.
- On CPU win (tier3 by any CPU): user loses the buy-in (already debited); `wallet.settleRound({ won: false, payout: bonusesEarned })`. Bonuses earned along the way are preserved in the payout even though `won` is false.

**No "draw" outcome.** The full call sequence (1..ballCount) is always drawn unless tier3 is claimed earlier; since every card has all its values within the ball-range, every card will achieve tier3 by the time all balls are called. The first CPU whose latency fires after the qualifying call always wins if user is in manual mode and never daubs. Tier3 will always be claimed.

### Bonuses

- Tier 1 (LINE) and tier 2 (TWO-LINE / FOUR-CORNERS) award chip bonuses **only to the user** and **only if the user's card is the first claimant** of that tier.
- If a CPU's card claims tier 1 or tier 2 first, no chips move — the only feedback is a banner ("Computer 3 got LINE!"). The user has lost their chance at that tier's bonus for this game.
- Bonuses accumulate in machine context (`bonusesEarned`) as they're claimed and are paid out as part of the **final `settleRound` payout** at game end. A user who wins LINE + TWO-LINE but loses tier 3 settles with `won: false, payout: 30` — the bonuses are preserved even on a tier-3 loss.
- The `WinBanner` shows "LINE! +10" the moment the user claims, but the actual balance bump happens at game end alongside any pot win. This keeps the wallet API surface unchanged (no new `creditChips` function) and keeps "one rounds row per game" intact.

### RTP

- **Easy:** 1 user card vs 2 CPU cards. P(user-win-pot) ≈ 1/3. EV(pot) = 100/3 ≈ 33. EV(bonuses) = 10/3 + 20/3 = 10. Total EV ≈ 43. RTP ≈ 86%.
- **Medium:** 1 vs 5. P ≈ 1/6. EV(pot) = 200/6 ≈ 33. EV(bonuses) ≈ 5. Total ≈ 38. RTP ≈ 76%.
- **Hard:** 1 vs 9. P = 0.1. EV(pot) = 40. EV(bonuses) ≈ 3. Total ≈ 43. RTP ≈ 86%.

Hard is "easier" in pure RTP terms but punishes the user with forced manual mode + instant CPU latency, so the practical RTP is lower depending on user reflexes.

## 7. CPU AI + race semantics

CPUs are statistical opponents, not strategic actors. Each CPU is a card + a fixed reaction latency.

### At game start

```typescript
const cpuLatencies = Array.from(
  { length: cpuCount },
  () => randomInt(latencyMs[0], latencyMs[1]), // each CPU rolls one fixed latency for the game
);
const cpuCards = Array.from({ length: cpuCount }, () => generateCard(rng, variant));
```

### Per ball call

The machine fires `CALL` (existing event from `useBingoBallCaller`). Action:

1. Append ball to `calledBalls`.
2. If `daubMode === 'auto'`, evaluate the user's card synchronously (0ms).
3. For each CPU, schedule a `CPU_DAUB { cpuIdx }` event via `setTimeout(..., cpuLatencies[cpuIdx])`.

When a scheduled `CPU_DAUB` fires:

1. Update that CPU's daub state (daub every called ball whose value is on the card).
2. Run `evaluateCardWins(cpuCard, calledSet, variant)`.
3. For each tier the card now satisfies that hasn't been globally claimed: emit `CLAIM { tier, source: 'cpu', cpuIdx }`.

### User in manual mode

- `CALL` does NOT auto-daub the user's card.
- User clicks cells; each click fires `MANUAL_DAUB { value }`.
- Machine validates: ball was called + cell isn't already daubed → updates daub state → re-evaluates user card → if a tier becomes satisfied AND that tier is unclaimed → emit `CLAIM { tier, source: 'user' }`.
- If user is slow: CPU latency expires first; CPU claims tier before user catches up.

### Tie-breaking

- Two CPUs with the same latency that both qualify on the same call: the lower-`cpuIdx` wins.
- User (0ms) vs a 0ms CPU on the same call: **RNG'd 50/50** (deterministic given seed). User does NOT get a free tie-break advantage on Hard.

### Cleanup

All pending CPU `setTimeout` handles MUST be cleared when:

- The machine transitions out of `playing` (tier 3 claimed → settling).
- The BingoPage component unmounts.

XState v5 actor `cleanup` callback handles this. Test coverage must exercise the cleanup path (game-end with pending timeouts).

## 8. State machine

Building on the existing XState v5 machine. The external event surface stays nearly identical to solo bingo; internal events and context fields grow.

### Context

```typescript
type Tier = 'tier1' | 'tier2' | 'tier3';

type CpuCardState = {
  card: BingoCard;
  daubed: boolean[]; // length = cellsPerCard (free centre starts true for American)
  latencyMs: number;
  hasClaimedTier1: boolean;
  hasClaimedTier2: boolean;
  hasClaimedTier3: boolean;
};

type BingoContext = {
  // EXISTING (shape preserved, some fields removed/renamed):
  gameId: string;
  variant: Variant;
  speed: BingoSpeed;
  daubMode: 'auto' | 'manual';
  callSequence: number[];
  callIndex: number;
  userCard: { card: BingoCard; daubed: boolean[] };
  betHandleId: string | null;
  betAmount: number;

  // NEW:
  difficulty: 'easy' | 'medium' | 'hard';
  pot: number;
  cpuCards: CpuCardState[];
  claimedTiers: Set<Tier>;
  userTier1: boolean;
  userTier2: boolean;
  userTier3: boolean;
  bonusesEarned: number;
  winner: { source: 'user' | 'cpu'; cpuIdx?: number } | null;
};
```

### Events

```typescript
type BingoEvent =
  | {
      type: 'BUY_AND_START';
      variant: Variant;
      difficulty: Difficulty;
      speed: BingoSpeed;
      daubMode: 'auto' | 'manual';
    }
  | { type: 'BET_PLACED'; handleId: string }
  | { type: 'CALL' }
  | { type: 'MANUAL_DAUB'; value: number }
  | { type: 'TOGGLE_DAUB' } // disabled on Hard
  | { type: 'CPU_DAUB'; cpuIdx: number } // internal, fires from setTimeout
  | { type: 'CLAIM'; tier: Tier; source: 'user' | 'cpu'; cpuIdx?: number } // internal
  | { type: 'SETTLED' }
  | { type: 'PLAY_AGAIN' };
```

### State graph

```
setup
  └─ BUY_AND_START → awaiting_bet_handle    (init context, request wallet placeBet)
awaiting_bet_handle
  └─ BET_PLACED → playing                   (store handleId, start ball caller)
playing
  ├─ CALL          → playing                (append ball, evaluate user if auto, schedule CPU evals)
  ├─ MANUAL_DAUB   → playing                (daub user cell, re-evaluate user card)
  ├─ TOGGLE_DAUB   → playing                (auto↔manual; manual→auto daubs all missed)
  ├─ CPU_DAUB      → playing                (daub CPU cells, re-evaluate that CPU)
  ├─ CLAIM (t1/t2) → playing                (mark claimed, credit user bonus if source='user')
  └─ CLAIM (t3)    → settling               (set winner, wallet.settleRound)
settling
  └─ SETTLED → done
done
  └─ PLAY_AGAIN → setup
```

### Shared helper

```typescript
function detectNewClaims(
  card: BingoCard,
  daubed: boolean[],
  variant: Variant,
  claimedTiers: Set<Tier>,
): Tier[] {
  const wins = evaluateCardWins(card, daubed, variant);
  return (['tier1', 'tier2', 'tier3'] as Tier[]).filter((t) => wins[t] && !claimedTiers.has(t));
}
```

This is the only place tier-claim detection happens. Both `CALL` (for user auto-daub), `MANUAL_DAUB` (for user manual-daub), and `CPU_DAUB` use it.

## 9. Persistence

### Rounds row

One row per game, written via `wallet.settleRound` when the machine transitions to `settling`:

```typescript
{
  game: 'bingo',                  // unchanged Round.game enum value
  stake: 50,
  payout: number,                 // bonusesEarned (loss) | pot + bonusesEarned (win)
  won: boolean,                   // tier3 claimant === 'user'
  details: {
    variant: 'british' | 'american',
    difficulty: 'easy' | 'medium' | 'hard',
    speed: 'slow' | 'normal' | 'fast',
    daubMode: 'auto' | 'manual',
    finalCallCount: number,
    cpuCount: number,
    userTier1: boolean,
    userTier2: boolean,
    userTier3: boolean,
    cpuTier3Winner: number | null,
    bonusesEarned: number,
    pot: number,
  }
}
```

Old solo-bingo `details` shape (`cardCount`, `fastFullHouse`, `perCardPayouts`) is dropped. Stats/leaderboard code reads `details` defensively (`??` fallbacks on missing fields) — old rounds rows in tester DBs need not migrate. Since no release between solo and competitive has shipped to anyone outside the project, this is acceptable.

### Wallet integration

- `wallet.placeBet(50)` → `betHandleId` at `BUY_AND_START`.
- Bonuses accumulate in machine context (`bonusesEarned`) as user claims tier 1 / tier 2; no wallet calls during play.
- `wallet.settleRound({ handleId, won, payout, details })` at game end. `payout = bonusesEarned + (won ? pot : 0)`.

No new wallet API is required. The existing surface (`placeBet` + `settleRound`) covers competitive bingo. Bonuses are batched into the final settle, which preserves the "one rounds row per game" invariant (ADR-0016).

- **Custom CPU AI personalities** — names, avatars, "slow grandma" / "speed demon" archetypes.
- **Per-CPU latency variation across calls** — latency is fixed per-CPU per-game.
- **Save / resume mid-game** — closing the tab forfeits the game.
- **Sound effects for ball calls + claim wins** — Phase 15.
- **Animated "ball drop" between draws** — currently a simple spring-in; could be a bouncing-around-a-bingo-cage visual.
- **Auto-call BINGO! when card qualifies in manual mode** — currently if you don't click within the race window you lose; could offer an "auto-call BINGO when reached" middle-ground.
- **History of past bingo games** — beyond what the rounds table already captures.

These will be appended to the `localgamble-deferred-features` memory.
